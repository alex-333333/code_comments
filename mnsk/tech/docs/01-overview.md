# 1. Обзор

## Что я исследую

Я сравниваю две группы комментариев к исходному коду.

| Группа | Как определяется | Почему так |
|---|---|---|
| **AI** | в сообщении коммита есть git-трейлер `Co-authored-by:` известного AI-инструмента (Claude, Copilot, Cursor) | Трейлер ставит сам инструмент, поэтому критерий детерминированный. У него нет собственной ошибки классификации, как у ML-детекторов вида «этот текст написан ИИ» |
| **Human** | коммит сделан **до 2020-11-01** и в нём нет AI-трейлера | До этой даты AI-соавторства в коммитах не было. Второе условие страхует от переписанной истории |

Единица наблюдения - один комментарий, а не файл и не коммит. Несколько строк `#` подряд я считаю одним
комментарием, докстринг тоже один.

## Гипотеза

> AI-комментарии в основном **референциальные**: они пересказывают то, что уже видно в коде. Человеческие
> чаще **объясняющие** и прагматические: они сообщают то, чего в коде нет («почему», «зачем», «осторожно»,
> «временно»).

Теоретическая рамка - прагматика. Операционализация - *lexical overlap* (см.
[03-methodology.md](03-methodology.md#6-lexical-overlap-единственная-величина-проекта-форма-твёрдая-параметры-рабочие)): доля слов комментария,
которые уже есть в соседнем коде. Если комментарий целиком состоит из слов, найденных в коде, он ничего не
сообщает сверх кода. На языке прагматики это высказывание с нулевой добавочной информацией.

### Что и в каком формате передаётся между шагами

| Этап | Вход | Выход | Формат |
|---|---|---|---|
| `discover_repos.py` | GitHub Search API | `ai_repos.txt/.jsonl`, `human_repos.txt`, `paired_repos.txt` | по `owner/repo` в строке |
| `parser.py` | список репозиториев | `corpus/manifest.jsonl` и `corpus/{ai,human}/…` | JSONL, файлы на нужной ревизии |
| `extract_comments.py` | манифест и файлы | `corpus/comments.jsonl`, `file_stats.jsonl`, `extract_stats.json` | JSONL: одно наблюдение на строку; статистика файла на строку (знаменатель плотности) |
| `counter.py` | `comments.jsonl` | `results/summary.json`, `examples.json`, `pool.jsonl`, `*.csv` | JSON / CSV (UTF-8 с BOM для Excel) |
| `dashboard.py` | `results/` | `dashboard.html` | один автономный HTML |
| `validate.py` | `results/pool.jsonl` | `gold_sample.csv`, `gold_key.csv`, `validation.json` | CSV / JSON |

Форматы подробно описаны в [04-reference.md](04-reference.md#форматы-файлов).

## Главные проектные решения

Каждое из них обосновано в [03-methodology.md](03-methodology.md). Здесь только список.

1. **Только строки, добавленные коммитом.** Иначе в AI-корпус попадут старые человеческие комментарии.
2. **`git log --grep -i -F`.** Регистр трейлера не важен: Claude Code пишет `Co-Authored-By`.
3. **Локальный git вместо GitHub API для выгрузки.** Нет лимитов запросов, результат воспроизводится.
4. **tree-sitter вместо `ast`/`tokenize`.** Нужны девять языков и положение комментария в дереве.
5. **Одна метрика (overlap) на всё.** Чекер измеряет тем же, чем корпус.
6. **Кривая чувствительности вместо одного порога**, плюс калибровка порога ручной разметкой.
7. **Бутстреп по репозиториям, а не по комментариям**: комментарии одного проекта не независимы.
8. **Docstring/JSDoc/Javadoc идут отдельным типом `doc`** и в основную метрику не входят.
9. **Словари лежат в данных, а не в коде**, поэтому их можно править как обычные CSV.

## Языки и расширения

`.py`, `.js`, `.jsx`, `.ts`, `.tsx`, `.java`, `.c`, `.h`, `.cpp`, `.go`, `.rs`: это 9 грамматик tree-sitter
(`python`, `javascript`, `typescript`, `tsx`, `java`, `c`, `cpp`, `go`, `rust`). Заголовки `.h` с
`class`/`namespace`/`template` разбираются грамматикой C++. Набор расширений задаёт, что такое корпус, поэтому
он записан в одном месте (`config.EXT_TO_LANG`), и менять его я буду только осознанно.

## Чего я здесь не делаю

- Не определяю по тексту, «написан ли комментарий ИИ». Критерий - трейлер.
- Не обучаю никакую модель: только счётчики, словари и статистика.
- Не оцениваю *качество* комментария, измеряю только его *функцию* (пересказ или объяснение).
- Не анализирую комментарии не на английском: словари английские.
